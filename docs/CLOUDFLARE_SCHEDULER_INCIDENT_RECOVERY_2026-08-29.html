1. 문서 목적

운영 서버의 실시간 데이터 수집이 멈췄을 때 원인을 빠르게 구분하고, 같은 장애를 5~15분 안에 복구할 수 있도록 실제 장애 사례와 복구 절차를 정리한다.

2. 장애 현상

운영 화면의 데이터 수집 완료 시각이 다음 값에서 더 이상 갱신되지 않았다.

데이터 수집 완료: 2026-08-28 16:53:18

운영 API와 Cloudflare KV의 마지막 저장 시각도 같았으므로 브라우저 캐시나 화면 표시 오류가 아니라 실시간 데이터 자체가 멈춘 상태였다. 시즌·문화 데이터는 이후에도 갱신되어 운영 페이지와 KV/R2 전체 장애는 제외할 수 있었다.

3. 확정된 원인

Cloudflare Cron Trigger는 실행됐지만 Worker에 전달된 실제 Cron 값은 다음과 같았다.

0,30 0-14,21-23 * * *

배포된 Worker는 아래 값을 실시간 수집 일정으로 정확히 일치 비교했다.

*/10 * * * *

SCHEDULES[controller.cron]에서 일치하는 키를 찾지 못해 다음 경고를 남기고 GitHub Actions 호출 전에 종료됐다.

{
  "cron": "0,30 0-14,21-23 * * *",
  "event": "unknown_cron",
  "level": "warn"
}
확정된 직접 원인
Cloudflare가 전달한 Cron 문자열과 Worker가 인식하는 Cron 문자열이 달랐다. Cloudflare Scheduled Event 자체는 성공처럼 보였지만 GitHub 워크플로는 호출되지 않았다.

이전 값이 전달된 배경은 이전 Trigger 잔존, 배포 중 설정 반영 불일치 또는 대시보드와 실제 이벤트의 전파 시점 차이 중 하나로 추정된다. 로그만으로 그중 하나를 단정하지는 않는다.

4. 원인 분리 과정

운영 데이터 확인

화면과 KV의 마지막 시각이 같아 화면 캐시 문제를 제외했다.

GitHub Actions 확인

Crawl Portal Trends and Upload의 실패 기록이 아니라 실행 기록 자체가 없어서 예약 호출 구간을 우선 점검했다.

수동 실행

GitHub에서 Run workflow를 실행해 성공했다. 따라서 크롤러, Actions 환경, 업로드 스크립트, 인증값, KV/R2 반영이 정상임을 확인했다.

Observability 확인

trafficcatcher-scheduler 로그에서 unknown_cron과 실제 Cron 문자열을 확인해 원인을 확정했다.

5. 실제 복구 절차

5.1 데이터를 먼저 응급 복구

  1. GitHub 저장소의 Actions를 연다.
  2. Crawl Portal Trends and Upload를 선택한다.
  3. Run workflow를 실행한다.
  4. 성공 후 운영 화면의 수집 완료 시각을 확인한다.

5.2 Cron Trigger 재등록

  1. Cloudflare Dashboard → Workers & Pages로 이동한다.
  2. trafficcatcher-scheduler를 선택한다.
  3. Settings → Trigger events → Cron triggers로 이동한다.
  4. 기존 Every 10 minutes Trigger를 삭제한다.
  5. + Add에서 */10 * * * *를 정확히 등록한다.
  6. 정기 수집 값 30 1,5,9,13,21 * * *는 유지한다.
  7. 설정 전파를 위해 최대 15분 기다린다.

Cloudflare Cron은 UTC 기준이지만 */10 * * * *는 시간대와 관계없이 24시간 매 10분 실행된다.

6. 복구 완료 확인

다음 네 항목을 모두 확인한다.
  • GitHub Actions에 수동이 아닌 새 자동 실행이 생성된다.
  • Crawl Portal Trends and Upload가 성공한다.
  • Observability의 Cron 값이 */10 * * * *로 표시된다.
  • 운영 화면의 완료 시각이 주기적으로 갱신된다.

정상 이벤트는 workflow_dispatched이며, unknown_cron이 다시 나오면 아직 정상화되지 않은 것이다.

9. 인증 오류일 때

workflow_dispatch_failed와 HTTP 401/403이 나오면 GITHUB_OWNER, GITHUB_REPOSITORY, GITHUB_REF, Secret GITHUB_ACTIONS_TOKEN을 확인한다. 토큰 값은 로그·문서·소스에 기록하지 않는다.

10. 재발 방지 권장 사항

  • Worker 배포 후 Trigger 두 개가 유지되는지 확인
  • 배포 직후 실제 controller.cron 값 확인
  • 마지막 수집 시각이 기준 주기의 2배 이상 오래되면 관리자 경고 표시
  • unknown_cron 관리자 알림 추가
  • GitHub Actions 자체 schedule을 보조 경로로 추가해 이중화
  • 마지막 정상 dispatch 시각을 KV/D1에 기록

이전 Cron 호환값을 코드에 추가할 때는 승인된 값만 명시적으로 허용해야 한다.
